# UI audit for a phone screen (portrait ~390x844, landscape ~844x390, coarse pointer, no hover)

Read-only audit of `/home/user/foolsfortune` (branch HEAD 4fa4652e). Prepared for Dovina's mobile plan. It reports what the code does; it designs nothing.

How this was made, and what it is not:
- Static reading of source, plus greps counted over `src/` and `index.html`. **No browser was run.** Every pixel figure below is computed from CSS constants and layout code, not measured. Where a figure is an estimate it says "est.".
- "dot" below means one dot of the 480-line present: `innerHeight / 480` CSS px (portrait 844 -> 1.76 px; landscape 390 -> 0.81 px; `brineframe.dot()` floors it at 1). Most of the HUD is built in dots.
- Verdicts: **works** (usable as is), **needs layout** (same interaction, new sizes/placement), **needs redesign** (the interaction itself assumes mouse/keyboard), **dev-only** (not a player surface).
- "Tap emulation": a touch browser synthesises mousemove/mousedown/mouseup/click after a tap, so click-only DOM windows may respond to taps by accident. Nothing in the repo is written or tested for this (no `touch*` handler anywhere), and drags, holds, hover and right-click have no emulation.

### Five sizing systems are in use (nothing shares a scale)
1. **Fixed CSS px**: the old windows (Codex, Index, Pneuka, shop, kiln, map, dialogue, pause card). Fonts 9 to 13 px.
2. **Viewport clamps**: `min(Npx, calc(100% - 24px))` on window widths (Codex 980, Index 720, dialogue 780, pause card 820, QAIS 860). Heights `calc(100% - 24px)` with `overflow:auto`.
3. **Dot units, `innerHeight / 480`** (overlay scene and the Brine-dress DOM): scales with height only, never width.
4. **`vh` units**: table HUD (`--u: calc(100vh / 1080)`), table action bar (`vh` widths with `max(12px, ..vh)` font floors), cinema bars (`--cine` in vh), stills (`vmin`).
5. **`vw`**: log width `min(40vw, 580px)`, portrait window `min(30vw, 440px)`, title logo `clamp(46px, 7.4vw, 96px)`.

## 3. Systemic issues (counts are from greps over `src/`, so approximate)

1. **No touch or gamepad input exists.** 0 `touch*` handlers, 0 `getGamepads`. 13 `pointerdown` listeners (all UI), 16 `mousedown`, 7 `mousemove`, 3 `mouseup`; look needs `movementX/Y` from `mousemove`.
2. **Pointer lock is the control scheme.** ~15 call sites request it; losing it pauses the game; where the API is missing nothing detects that (see Section 1). Every window's `onClose` re-requests it.
3. **Hover carries information.** 23 JS hover handlers in 15 files (`mouseenter`/`pointerenter`/`mouseover`) and 37 CSS `:hover` rules in 19 files. Information that exists only on hover: the Pneuka Box and shop hover line (what a click does, the price, "right click: haggle"), keyword tips, table tips, kiln glaze descriptions, composer ghost, race-board PAINT preview, pier mount preview, garage notch change, god-hand art tip, hover-lift of table pieces, duel cell hover. Choice cards are the one exception: a 420 ms hold already shows the detail.
4. **`title` attributes** as tooltips: about 45 to 55 uses in ~30 files (Codex switches, status chips, tier points, composer pieces, lend switches, practice-card pips, calibrate button, kiln swatches, garden chips, chat `.min`).
5. **Right-click is a required input** in at least 10 UI places (Pneuka menu, underside reverse, shop haggle, map clear, composer rotate, duel drop, editor remove, god-hand wheel, Soul Brush paper, lock-on). 54 `contextmenu`/`Mouse2` lines; `core/input.js` swallows the browser menu.
6. **Drag is required.** HTML5 drag-and-drop in 3 files (pneuka/ui.js, readingtable.js, underside.js); mouse-drag pan in the map; drag-to-turn in the kiln; hold-and-move path in the puzzle duel; free-cursor drags for every god art; the track editor point drag (this one uses pointer events).
7. **Mouse wheel** is a required input for map zoom, god-hand zoom, editor zoom, log scrolling, the psygun cylinder, the Lockheart's wheel (99 `wheel` references, including radial wheels).
8. **Keyboard is the only trigger** for every window listed in the Section 1 key list; 322 key reads in play; typed input exists in the seal picker (Key A..Z, no DOM input), reprogram (hidden input), rhythm mode (10 lane keys), and the chat line (a real `<input>`).
9. **Fixed-px widths over 300 px**: Pneuka `.equip` 560 + `.bank` 434, reading table 560 x 640, underside min 880, shop shelf 330, kiln 330, radial wheel 300, god wheel 340, reprogram min 360, bug markup side 320 (dev). About 12 declarations in 9 player-facing files. Pneuka and the underside are rescued by `fit()` scaling, at est. k = 0.34 to 0.41 (text about 4 px).
10. **Small type**: about 150 font declarations at 11 px or less across ~30 files (some are canvas-drawn); common values 9, 10, 11 px in the Pneuka, shop, kiln, codex rows, composer cells, log tabs/foot (9.5 px).
11. **Small hit targets (< 40 px)**: Codex/Index/Pneuka CLOSE (about 20 to 22 px tall), log tabs and `.min` (about 18 px), Codex shelf tabs (about 18 px), buttons in Codex/shop/kiln (about 20 to 29 px), dialogue options (about 28 px), map buttons (about 26 px), composer cells 46 px (ok), pocket slots 52 px before the Pneuka scale-down (about 18 px after). Choice cards and Index rows are tall enough. No `min-height: 44px` convention exists.
12. **Four different scale origins** (Section 1): the table HUD's `100vh / 1080`, the rail/goals DOM's `innerHeight / 480`, the overlay scene's `H / 480`, the log's `vw`/`vh`. All scale by height only, so portrait enlarges height-keyed UI (the dot is 1.76 px) while the width stays 390 px: the bottom-right stack (tube 227 px + cylinder centred 357 px from the right) already exceeds the width.
13. **Collisions between HUD zones** are by hand: the bottom-right stack is placed by published widths (`lachrimeterTube.pubW` etc.); the log (bottom-left), `seahud` (left 18, bottom 200) and the table action bar (bottom-centre) have no layout manager. In portrait the log (156 px) and the tube (227 px) sum to 383 of 390 px.
14. **Responsive rules that exist are width-only column collapses** at 560 to 900 px. They would trigger on a phone, but the windows underneath keep 18 to 22 px padding and a 14 px nine-slice frame (theme.js), so a 390 px window has about 340 px to work with before content, and the raceboard's inline 7-column grid defeats its own media rule.
15. **No safe-area, no `dvh`, no fullscreen, no orientation lock, no PWA metadata.** The `#loading`, `#overlay` and the `body.overflow:hidden` shell will have the browser's URL bar resize the viewport mid-play (`100vh` users: table HUD, Pneuka menu, `--cine`).
16. **The glove cursor system** (theme.js `jglove`, `--jcur`, `--jcur-pointer`, `jgrab`, `optionAt()` via computed `cursor`) assumes a hover pointer; harmless on touch but it drives menu sounds and the keyboard selection state (`.sel`) that several windows use as their only highlight.
17. **Word/UI rules to keep in mind** (from CLAUDE.md, not code facts): words belong in windows, the log and the overlay; world marks carry none; the log is the only narration. A touch layer would be new UI under these rules (the UI is never stock; Calissa owns `src/ui`, `src/vfx`).

## 5. Not verified

- No page was loaded in a browser or an emulator; every size is derived from CSS constants. In particular: Pneuka natural height (est. 900 px), the Sight's true width (est. from `ORIGIN` and the unit scale), the results window's overflow, the log's usable text width under the 14 px frame.
- Whether Chrome for Android grants pointer lock was not checked here; the code path for "API absent" was read (Section 1).
- Tap emulation of `mousemove` before `mousedown` is browser behaviour assumed from general knowledge, not tested against this build.
- Contents of the Codex pages beyond their CSS (row counts, text length) and each Index page's final DOM were not rendered.
- `src/world/*` rooms, `src/vfx/*` looks and `src/world/garden/*` were read only where they build DOM or place overlay-scene objects; other files in those folders draw in the 3D world and are out of scope.
